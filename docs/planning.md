# Короткий план и продолжение исследования

Версия 0.2 сохраняет формат дела `schemaVersion: 1` и добавляет необязательный контекст вопросов. Старые дела читаются без миграции. Планировщик выбирает следующий проход, а агент проверяет коллекции и выполняет поиск браузером.

## Три действия по умолчанию

```bash
node bin/drevo.mjs plan ../my-family-case/case.json
node bin/drevo.mjs plan ../my-family-case/case.json --limit 2
node bin/drevo.mjs plan ../my-family-case/case.json --all
node bin/drevo.mjs plan ../my-family-case/case.json --paid
```

Обычный вывод показывает три доступных бесплатных действия. Вначале рассматривается первый открытый вопрос с наивысшим приоритетом; порядок одинаковых приоритетов сохраняется из дела. Если у вопроса меньше трёх доступных шагов, список дополняется следующим вопросом. `--all` раскрывает все доступные действия, связанные завершённые проверки и препятствия. `--paid` показывает лишь платные предложения с конкретным основанием.

В учебном деле первой версии обычный план выдавал **38 бесплатных пунктов и 18 платных кандидатов** — 518 строк. После изменения обычный вывод содержит **3 действия**: «Карта захоронений», «Помним Онлайн», BillionGraves. Остальные 35 бесплатных маршрутов остаются в резерве. Эти числа — проверенный пример, не постоянный лимит реестра и не результат выполненного генеалогического поиска.

Приоритет зависит от вопроса: для погребения раньше идут мемориальные базы, для трудовой биографии — архивы и местные документы. Затем учитываются приоритет ресурса, известный регион и проверенность входа. Это порядок работы, не оценка достоверности найденного родства.

## Контекст одного вопроса

```json
{
  "id": "q-work",
  "personId": "p1",
  "question": "Где искать кадровую запись?",
  "recordTypes": ["employment"],
  "priority": "high",
  "status": "open",
  "context": {
    "event": "employment",
    "period": {"from": 1950, "to": 1960},
    "regions": ["vologda"],
    "place": "Населённый пункт из документа",
    "institution": "Название учебного учреждения",
    "jurisdiction": "Исторический район — проверить по справочнику",
    "collectionId": "",
    "coverageId": "first-index-pass"
  }
}
```

Пример вымышленный; идентификатор человека должен существовать в `people`.

- `status`: `open`, `resolved`, `paused`. Если отсутствует, вопрос открыт. Решённые и отложенные вопросы не порождают новые действия.
- `event`: `birth`, `death`, `burial`, `marriage`, `employment`, `military`, `residence`, `general`. Без него тип осторожно выводится только для захоронений, работы или службы; остальные вопросы считаются общими.
- `regions` заменяет географию дела для этого вопроса. Область включает общероссийские источники через `regionParents`; страна не открывает автоматически все областные архивы.
- `period` заменяет общий период. Для явного рождения используется известный год рождения; для смерти/погребения — год смерти, если период вопроса не задан. Для службы год рождения не подставляется как год войны. Если год семейной версии приблизителен, агент задаёт подходящий диапазон явно.
- `place`, `institution`, `jurisdiction` описывают конкретное событие. Планировщик не устанавливает старое административное подчинение самостоятельно: агент проверяет его по документу или справочнику.
- `query` позволяет задать один точный запрос вместо автоматически составленных вариантов. `collectionId` — устойчивый идентификатор коллекции или дела. `coverageId` — идентификатор конкретного охвата, например индекса по одному году или листов 1–20. Это локальные метки, не вымышленные архивные шифры.

В `queryFields` результата отдельно передаются варианты имени, место, учреждение, событие и период. Строка `queries` — подсказка запроса; её нельзя целиком вставлять в поле «Фамилия». Браузерные инструкции ресурса объясняют, как распределить сведения по полям. Если пока известна только область, первый шаг — проверить покрытие и уточнить место, а не объявлять найденную карточку нужным родственником.

## Что делает временной фильтр

У части маршрутов в реестре есть `recordPeriod` со ссылкой на первичное описание. В `recordPeriod.eventTypes` указано, для какого события этот диапазон применим. При непересекающихся периодах **одного временного основания** маршрут не предлагается; причина остаётся в `excluded` JSON. Известные сейчас примеры: Первая мировая 1914–1918, маршрут участников Второй мировой 1939–1945, фотографии 1840–1999. Для ОБД «Мемориал» описаны ВОВ и послевоенное время, поэтому верхняя граница не выдумана.

Это период исследуемого события, не дата рождения всех упомянутых в документе людей и не дата создания поздней копии. Если нужно изучить военную службу человека, родившегося в 1912 году, вопросу задают годы службы. Если вопрос о рождении 1912 года предлагает поискать эту дату в военной карточке, диапазон WWII не исключает источник: он относится к службе, а 1912 — к рождению. Такой шаг получает `coverageStatus: period-needs-context`; агент отдельно уточняет период документа. Диапазон ресурса не обещает полноты каждого года.

Для остальных ресурсов результат имеет `coverageStatus: period-unknown`. Сначала нужно установить годы конкретной коллекции. Неизвестный охват не превращается ни в полное покрытие, ни в исключение ресурса. Основания диапазонов доступны в `registry/resources.json` → `recordPeriod.evidenceUrls`.

## Как избежать повторов

Каждое действие получает устойчивый `actionKey`. Он описывает ресурс, человека, варианты запросов, событие, период, географию, место, учреждение, юрисдикцию, коллекцию и охват. Название вопроса и порядок вопросов в ключ не входят. Одинаковая проверка, отвечающая на два вопроса, отображается один раз с несколькими `questionIds`.

После **фактически выполненного** действия сохраните в `completedSearches`:

```json
{
  "resourceId": "pomnim-online",
  "personId": "p1",
  "actionKey": "скопировать точный ключ из плана",
  "query": "фактически выполненный запрос",
  "collectionId": "",
  "coverageId": "first-index-pass",
  "coverage": "Какие запросы, фильтры, годы, страницы или кадры действительно просмотрены",
  "result": "not-found",
  "checkedAt": "2026-11-11",
  "repeatReason": ""
}
```

`actionKey` копируется из плана, а не придумывается. Запись с совпавшим ключом и результатом `found`/`not-found` переводит эту проверку в `completed`; `blocked` — в отдельный список препятствий. `not-searched` не закрывает действие. Порядок добавления строк журнала определяет последнее состояние.

**Не помечайте весь ключ выполненным, если просмотрена только часть запланированных запросов или листов.** Создайте точный `query`/`coverageId` для проверяемой части и получите её ключ. Журнал хранит фактический охват, а не обещание прочитать остальное.

Новый запрос, другая коллекция или охват создают новый ключ. Старый отрицательный результат не исключает сайт целиком. Старые журналы без `actionKey` сохраняются в истории; автоматически закрыть действие они могут только для **одного** запланированного запроса при его совпадении и явно заданных `coverageId`/`collectionId`. Один старый запрос не закрывает действие с несколькими вариантами имени.

Для осмысленного повторного прохода укажите `question.context.repeatReason`, например «появилось новое фото с точным отчеством» или «пользователь предоставил авторизованную сессию». После прохода сохраните эту же причину в строке журнала. Следующий план не будет повторять действие бесконечно на основании той же причины. Изменение одного результата без нового основания не означает нового поиска.

## Когда появляется платное предложение

Даже с `allowPaid: true` план ничего не покупает. В контексте вопроса должны одновременно присутствовать:

```json
{
  "paidResourceId": "ancestry-paid",
  "collectionId": "точный идентификатор проверенной коллекции",
  "paidReason": "Какая нужная запись здесь обнаружена и почему бесплатного пути недостаточно"
}
```

Тогда предложение попадает в `paidOptions` и раскрывается флагом `--paid` или `--all`. Поле не подтверждает истинность предпосылки: агент проверяет покрытие, наличие материала, действующую цену и условия. Остальные совпавшие по типу записи платные сайты остаются скрытыми кандидатами, а не рекомендациями оплатить их. Полный справочный список доступен отдельно: `sources --paid`.

## Результат для другого инструмента

`buildPlan(data, registry, {all: false, limit: 3, paid: false})` возвращает:

| Поле | Значение |
|---|---|
| `nextActions` | Три следующих действия либо весь бесплатный список при `all:true` |
| `reserve` | Не показанные в коротком плане доступные действия |
| `freePlan` | Полный список доступных бесплатных действий для совместимости; без завершённых и заблокированных |
| `completed`, `blocked` | Совпавшие с текущими действиями записи соответствующих состояний |
| `paidOptions` | Кандидаты с конкретным ресурсом, коллекцией и основанием |
| `paidReserve` | Необоснованные кандидаты; текстовый вывод их не рекомендует |
| `excluded` | Маршруты вне известного периода с объяснением |
| `skippedQuestions` | Вопросы со статусом `resolved`/`paused` |
| `warnings` | Недостаточный контекст и неподдержанные коды |

`--json` сохраняет подробные резервные массивы для агента. Обычный текст остаётся коротким. Ни одно состояние плана не устанавливает историческую истинность; исходный журнал и документы продолжают храниться в частном деле.
