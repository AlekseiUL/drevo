# Данные просмотрщика

Минимальный вход:

```json
{
  "title": "Наша семья",
  "rootPerson": "person-1",
  "persons": [{"id":"person-1","name":"Известное имя","confidence":"reported"}],
  "connections": [],
  "families": [],
  "relationships": []
}
```

`id` состоит из латинских букв, цифр, `_` и `-`; он уникален и не меняется при уточнении имени. `rootPerson` задаёт выделенный лист. Поле `demo:true` предназначено только для вымышленных примеров.

Человек может иметь `birthYear`, `deathYear`, точные `birthDate`/`deathDate` в формате `YYYY-MM-DD`, `lifeStatus` (`living`, `deceased`, `unknown`), `place` и `aliases` — массив вариантов имени. Неизвестные даты пропускаются. Приложение не выводит смерть из возраста.

`birthApproximate:true` или `deathApproximate:true` сохраняет знак ≈ перед датой. Для конкурирующих годов используются `birthYearCandidates:[1910,1912]` и `deathYearCandidates:[1985,1987]`; они показываются как «1910 или 1912». Альтернативы не совмещаются с одной выбранной датой того же события: конфликт останавливает сборку. Необоснованную середину диапазона не записывают как точный год. Иные виды неопределённости поясняются в согласованном `publicNote`.

Календарная дата проверяется на существование. Год и точная дата одного события должны совпадать. Хронология сравнивается с учётом того, что отдельный год означает весь календарный год; невозможный порядок рождения и смерти отклоняется. Для дат с неопределённой приблизительностью строгая хронологическая граница не выдумывается. Эти правила не означают полной совместимости со сторонними форматами.

## Отдельные отношения: формат v0.2

Новые проекции исследования используют `connections`. Каждая связь имеет собственное основание и набор утверждений:

```json
{
  "id": "parent-1-child-1",
  "a": "person-1",
  "b": "person-3",
  "type": "parent-child",
  "confidence": "reported",
  "claimIds": ["claim-parent-1"],
  "evidence": [{
    "claimId": "claim-parent-1",
    "statement": "В семейном рассказе человек 1 назван родителем человека 3.",
    "status": "family-story",
    "sources": [{
      "id": "interview-1",
      "title": "Запись семейного рассказа",
      "url": "",
      "locator": "Разрешённый к показу фрагмент 2",
      "reading": "Дословно прочитанная или услышанная фраза",
      "reasoning": "Почему эта фраза относится к данному утверждению",
      "information": "undetermined",
      "type": "direct",
      "form": "authored",
      "accessedAt": "2026-11-11"
    }],
    "conflicts": [],
    "conclusion": null
  }]
}
```

Это пример структуры, не настоящее свидетельство. Для родительских связей `a` — родитель, `b` — ребёнок. Типы: `parent-child`, `adoptive`, `guardian`, `partner`, `sibling`. Два последних симметричны. Наличие двух родителей одного ребёнка выравнивает карточки для показа, но не создаёт им супружескую связь автоматически. Опека показывается в сети, исключаясь из предков/потомков; усыновление подписывается отдельно.

ID связи уникален. Несколько утверждений об одном отношении объединяются в `evidence` одной связи, а не создают несколько одинаковых линий. Идентификаторы утверждений перечисляются в `claimIds`. Статусы утверждения: `family-story`, `candidate`, `hypothesis`, `documented`, `concluded`; это не то же поле, что `confidence` линии. Корневая проекция Древа выбирает допускаемые утверждения; viewer не повышает статус самостоятельно.

Необязательная строка `evidence[].assertionLabel` передаёт читаемое значение типизированного утверждения, подготовленное проекцией. Она выводится под текстом как «Для дерева: …». Например, при отображении двух конкурирующих годов на карточке в основаниях сохраняются обе исходные точные даты. Viewer не вычисляет эту подпись из свободного текста и не превращает её в новое доказательство.

У источника сохраняются только `id`, `title`, `url`, `locator`, `reading`, `reasoning`, `information`, `type`, `negativeScope`, `form`, `accessedAt`. `information`: `primary`, `secondary`, `undetermined`. `type`: `direct`, `indirect`, `negative`. Для отрицательного свидетельства `negativeScope` объясняет, почему запись ожидалась и какой объём проверен; отсутствие этого объяснения явно отмечается. `form`: `original`, `derivative`, `authored`, `unknown`. URL — HTTP(S) либо пустая строка; другая схема ссылки удаляется из публичной проекции. Источник без веб-ссылки остаётся читаемым по названию и локатору.

Противоречие: `{"description":"Что расходится","status":"open","resolution":""}`. После разбора используется `resolved` с объяснением. Открытый конфликт виден в линии, карточке и панели оснований даже при `confidence:documented`. Вывод: `{"text":"Итог","reasoning":"Аргументация","limitations":"Что остаётся неизвестным"}` или `null`.

Такая же `evidence` может находиться у человека: например, источники года рождения или места смерти. Кнопка в его карточке открывает основания этих сведений. Происхождение каждого отношения доступно через «Почему эта связь?» в панели, выбранном пути и по нажатию на ветвь; ветвь доступна также с клавиатуры.

Поля `notes`, `path` и другие частные метаданные не копируются сборщиком. Тексты утверждений, локаторов и прочтений считаются уже разрешёнными для данного просмотра: allowlist не анонимизирует содержимое текста. Для публичной версии используйте отдельную проверенную проекцию из исследовательского дела.

## Совместимость с первоначальной схемой

Прежняя семья поддерживается: `{"id":"family-1","parents":["person-1","person-2"],"children":["person-3"],"relationshipType":"parent-child","confidence":"reported"}`. Один родитель допустим. Пара без детей использует `partners` вместо `parents`. Несколько семей могут ссылаться на одного человека. Одна общая метка семьи применяется ко всем её родительским линиям. Если у них разные основания, используйте `connections`.

Братья/сёстры с неизвестными родителями: `{"id":"sibling-1","kind":"sibling","a":"person-1","b":"person-2","confidence":"reported"}` в `relationships`. Общих родителей для оформления не придумывают.

У человека и каждой связи независимое поле `confidence`: `documented` — документальное основание; `reported` — сообщение семьи; `hypothesis` — версия; `unknown` — основание не указано. Viewer показывает метку, но не проводит самостоятельную экспертизу доказательств. Путь сначала ищется без гипотез, при необходимости показывается версия с предупреждением.

При наличии нескольких маршрутов поиск предпочитает путь без гипотез и открытых конфликтов. Старые и новые отношения могут сосуществовать, но дублирование одного отношения в двух форматах отклоняется. Для новой проекции оставляйте `families`/`relationships` пустыми. При отсутствии прикреплённого `evidence` viewer честно показывает, что обоснование пока не передано.

Публичные поля: `sourceLabel`, `publicNote`, `publicSources:[{"label":"Описание","url":"https://example.org/record"}]`. Допускаются только HTTP(S) ссылки. `notes`, `references`, `source` и любые другие неоговорённые поля сборщик не экспортирует. Это не автоматическая анонимизация: имена, даты, места и публичные тексты публикуются буквально.

Фотография: `"portrait":{"kind":"original","path":"assets/photos/person.jpg"}`. Поддерживаются PNG, JPEG, WebP, AVIF; путь локальный, внутри `public/assets/photos/`, без переходов вверх. `generated` означает воображаемый портрет; `selected` — изображение, выбранное владельцем. Входные сканы и фото, которые не должны публиковаться, держат в `private/`.

Неподдерживаемые форматы (например GEDCOM) сначала явно преобразуются агентом в этот JSON со сверкой числа людей, связей и источников. Автоматического GEDCOM-импортёра нет. Ручные координаты и сложные межпоколенные браки в первой версии не поддерживаются; конфликт поколений останавливает сборку вместо искажения дерева.

## Досье человека: формат v0.3

У человека появилось необязательное `dossier`. Оно собирает описание жизни и деятельности, прикреплённые материалы и все переданные находки. Связи дерева по-прежнему определяются только отдельными отношениями; добавление фотографии или документа не устанавливает родство.

```json
{
  "dossier": {
    "biography": "Краткое описание жизни.\nАбзацы сохраняются.",
    "activity": "Работа, учёба, служба, общественная деятельность и увлечения.",
    "materials": [{
      "id": "archive-page-1",
      "title": "Страница архивного дела",
      "kind": "document",
      "description": "Что изображено и чем материал полезен",
      "date": "1930-е — датировка требует проверки",
      "sourceId": "archive-source-1",
      "sourceLabel": "Название архива или владелец оригинала",
      "sourceUrl": "https://example.invalid/catalogue",
      "locator": "Фонд, опись, дело, лист/кадр",
      "rights": "Основание разрешённого использования",
      "path": "assets/materials/archive-page-1.pdf",
      "url": "",
      "fileName": "archive-page-1.pdf"
    }],
    "findings": []
  }
}
```

Это пример формата. `findings` — массив утверждений того же формата, что `evidence` выше. Он может включать семейные сообщения, кандидатов, гипотезы и противоречия, ещё не включённые в линии дерева. Viewer сохраняет их статусы и открывает точные основания. Соответствие `sourceId` реестру исследования проверяет основная проекция дела; standalone viewer хранит переданную ссылку и подпись, но не имеет отдельного реестра источников.

`biography` и `activity` — обычный текст, без HTML. Неоговорённые поля досье и материалов, например частные заметки или путь к оригиналу, отбрасываются. Содержимое разрешённых текстовых полей не анонимизируется: для публичного размещения сначала подготовьте согласованный состав данных в основном деле.

ID материалов уникальны внутри карточки; состоят из латинских букв, цифр, `_`, `-`. Метаданные без доступного файла допустимы: например, каталожная находка с `url` или шифром. Отсутствующий/пустой `path` не превращается в обещание наличия скана. `url` и `sourceUrl` принимают HTTP(S); внешние страницы открываются по ссылке и не встраиваются автоматически.

Файлы находятся в `public/assets/materials/`. Путь строго имеет вид `assets/materials/<id>.<расширение>`, без подпапок, абсолютных путей и переходов вверх. `kind` файла должен совпадать с его форматом:

| Вид | Форматы | Просмотр |
|---|---|---|
| `photo` | PNG, JPG/JPEG, WebP, AVIF, GIF | Изображение |
| `document` | PDF, UTF-8 TXT | PDF или текст в карточке |
| `document` | TIFF, DOC/DOCX, ODT, RTF, CSV, XLS/XLSX | Скачивание оригинала |
| `audio` | MP3, WAV, OGG, M4A | Встроенный плеер без автозапуска |
| `video` | MP4, WebM, MOV | Плеер; поддержка кодека зависит от браузера |
| `other` | ZIP | Скачивание |

HTML, SVG, JavaScript и исполняемые файлы в материалы не принимаются. Шрифт и встроенная иконка viewer остаются контролируемыми ресурсами интерфейса. Тип ответа и `preview` вычисляются по разрешённому формату, а не принимаются из произвольного `mediaType`. Необязательные `size` (размер в байтах) и `sha256` проверяются при сборке. Подпись формата встроенно просматриваемых файлов сверяется с содержимым; это защита от ошибочного расширения, не антивирусная экспертиза.

Сборщик переносит только файлы, на которые действительно ссылаются карточки. Отсутствующий материал, изменение ожидаемого размера/хеша или символическая ссылка за пределы `public/` останавливают сборку. Оригиналы остаются неизменными; производные изображения и расшифровки оформляются отдельными материалами с пояснением происхождения.

Чтобы сразу перенести подготовленные файлы при создании viewer:

```bash
node <skill>/scripts/create-project.mjs --out <новая-папка> --data <family.json> --assets-dir <public-root>
```

`<public-root>` содержит `assets/materials/` и при необходимости `assets/photos/`. Копируются только указанные в данных файлы. С явным `--data`, но без `--assets-dir`, можно скопировать их вручную в новую папку до сборки. Демо без `--data` уже включает собственные вымышленные материалы.

Статический viewer показывает готовое досье. Редактирование описания, загрузка и отсоединение материалов доступны при запуске локального семейного дела через основную команду Древа; изменения сохраняются в его канонических файлах. У опубликованного статического демо нет записи в семейное дело.
